# Amami Creature Markdown Writer

奄美大島のナイトツアーサイト(Nature Experience Amami)は、`content/creatures/カテゴリー/生き物ID.md`という
Markdownファイルを正本として、そこから個別ページ・図鑑ページ・関連カード・トップの「ナイトツアーで出会える生き物」の写真・
AIチャット用の`data/creatures.json`を自動生成している。
このスキルは、その正本となるMarkdownを「事実確認済み・書式統一済み」の状態で書き、サイトに反映するまでの手順をまとめたもの。

オーナーは関西弁で話す、奄美のナイトツアーガイド。返事は日本語で、専門用語はかみくだく。

## このスキルの読み方

- **決まり**: 答えが一つに決まっていて、外すとサイトが壊れる・事実を間違える・オーナーの確認を飛ばすことになるもの。必ず守る
- **目安**: 見本やふだんのやり方。状況に合わせて変えてよい。迷ったら既存ファイルに合わせる

「絶対に守ること」「ファイルの書式」の frontmatter の項目名と値・1行目の学名の形・id・danger のキーワード・activity と night_observable・サイトへの反映手順は**決まり**。
文章の言い回し、段落の組み立て、調べる順番、名前の付け方の例、報告の書き方は**目安**。

## ハルシネーション禁止(決まり。いちばん大事)

サイトは実在の生き物を紹介し、訪れた人がそれを信じる。確かめていないことを本当らしく書くのは、どんなに小さくても禁止。

- 書くのは、情報源で確かめられたことだけ。記憶や「たぶんこうだろう」で数値・学名・分布・生態・保護の指定を書かない
- 情報源・論文名・著者・年・URLを作らない。実際に見たものだけを source に書く
- 検索結果の要約しか読めなかったものは、そうだと分かるように報告する(要約は取り違えが多い。例: 2026年の論文を奄美の初記録と書いてしまった)
- 分からないことは、書かないか「〜とされる」「詳しいことは分かっていない」と書く。空欄は間違いより良い
- オーナーへの報告でも同じ。確かめていないのに「できた」「消えている」「正しい」と言わない

## 絶対に守ること(決まり)

1. **ファイル作成の前に、必ずWeb検索で最低2つ以上の情報源を確認する。** 記憶だけで学名・大きさ・生態を書かない。
2. **最新の論文まで確認する。** 学名や分類はよく変わる(例: チンメルマンセスジゲンゴロウは2026年の論文で *Copelatus* から *Austrelatus* に移された)。「学名 + 今年の年」「英語の学名 + new record / comb. nov.」でも検索し、直近の論文があれば新しい方に合わせる。オーナーが「新しい論文が出てるはず」と言ったら、まずそれを探す。
3. **「初記録」「〇〇で初めて確認」は、元の文献で確かめられたときだけ書く。** 検索結果の要約は「新記録」を取り違えやすい(2026年の論文を奄美の初記録と書いてしまい、実際はMorii (2018)が最初だった例がある)。確かめられなければ「〇〇からも記録がある」程度にとどめる。
4. **似た用語を取り違えない。** 例: カエルの「背中線」(背中の真ん中の1本)と「背側線」(背中の両脇の2本)は別物。資料の言葉をそのまま比べる。
5. **情報が薄い・情報源同士が食い違う・ページを直接読めなかった(検索の要約でしか確認できなかった)ときは、正直にその旨を伝える。** 分からないことを断定で書かない。
6. **書き終わったら、確認してほしい点を短くまとめてオーナーに伝える。** 黙って完成品だけ出さない。オーナーは手元の写真で確かめてくれることが多い(例: 「俺の写真は白い線はいってない」)ので、写真で確認できる点はそう頼む。

## 進め方(決まり。オーナーとの約束)

1. 下書きを作り、**コミットする前に、コピーできる形でチャットに貼る**(ファイルの置き場所とファイル名も書く)。
2. **作り終わったら監修を通す。** Claude Codeで作業している場合は、下書きを `content/creatures/カテゴリー/生き物ID.md` にファイルとして保存し(まだコミットしない。監修役はファイルを読んで確認するため、チャットに貼っただけでは監修できない)、そのパスを伝えて監修役 `creature-reviewer`(`.claude/agents/creature-reviewer.md`)で監修し、結果をオーナーに見せてから完了とする。監修役を呼べない環境(claude.aiのチャットなど)では、「Claude Codeで creature-reviewer に監修を依頼してください」とオーナーに伝える。
3. オーナーの指摘と監修の結果を反映する。指摘された根拠が別のことを言っていないかは確かめてから直す(上の4番)。
4. 「コミットして」と言われたら:
   - 日本語mdをリポジトリに置く
   - 翻訳(`.en.md`・`.es.md`・`.zh.md`)も作る → `amami-creature-translation` スキルを使う
   - ページを作り直す(下の「サイトへの反映」)
   - コミットは2つに分ける(mdの追加/ページの再生成と記録)
   - `PROJECT_STATUS.md` の変更履歴に追記する(`amami-project-status-log` スキル)
   - プッシュしてプルリクエストを作り、URLを伝える
5. 「マージして」と言われたらマージする。マージは必ずオーナーの指示を待つ。

## ファイルの書式

### frontmatter

```yaml
---
id: 生き物id                # 写真フォルダ名と完全に一致させる(下記)
name: 表示名(カタカナの標準和名)
category: カテゴリーid        # 下の表のどれか
group: グループid            # 図鑑形式のカテゴリーと両生類で使う(下の表)
danger: 危険度・保護状況      # 下記。確認できなければ書かない
months: [観察しやすい月]      # ナイトツアーで観察しやすい月。オーナーに聞く。無ければ写真の撮影日から自動集計
activity: nocturnal          # nocturnal(夜行性) / diurnal(昼行性)。オーナーに聞くのが確実
night_observable: true/false # 下記。必要なときだけ
source: 情報源               # 図鑑形式の種では書くことが多い。論文は著者・年・誌名・巻号・ページまで
---
```

### カテゴリーとグループ

| category | 形式 | group の例 |
|---|---|---|
| snakes | 個別ページ | なし |
| amphibians | 個別ページ | frog(カエル) / newt(イモリ) |
| lizards | 個別ページ(一覧ページはまだ無い) | なし |
| stag-beetles | 個別ページ | なし |
| mammals | 個別ページ | なし |
| birds | 図鑑 | suzume, buppousou, fukurou, taka, kitsutsuki, hato, chidori, other |
| beetles | 図鑑 | funchu, kabuto, hanamuguri, manmaru, tamamushi, kamikiri, hamushi, other |
| aquatic-insects | 図鑑 | gengoro, doromushi, amenbo, mizumushi, gamushi, other |
| other-insects | 図鑑 | tyou, tombo, ga, tyokushi, other |

グループの正式な一覧は `scripts/generate_zukan_page.py` の `CATEGORY_GROUPS`。
カニ(`crustaceans`)とその他の節足動物(`other-arthropods`)は写真だけあり、カテゴリーページの形を決めるのが先(`amami-new-category-page` スキル)。

### 本文

**決まり**: 1段落目は必ず「科名属名 *学名*」の形にする(自動処理で学名行をヒーロー部分に分離するため)。属の和名が無いときは亜科までで止める(例: 「ゲンゴロウ科セスジゲンゴロウ亜科チンメルマンセスジゲンゴロウ *Austrelatus zimmermanni* (Gschwendtner, 1934)」)。

```
科名属名 *Genus species*

大きさ○○cm(または○○mm)。分布・生息環境・見た目の特徴・行動・注意点などを、1段落で簡潔にまとめる。
```

**目安**: 既存ファイルは体言止め・簡潔な断定文が多い。装飾的な形容詞は避け、事実ベースで書く。長さや書く順番は種に合わせて自由に(情報が多い種は詳しく、少ない種は短く)。
学名が最近変わった種は、本文で一言触れるとよい(例: 「長く〇〇属とされてきたが、20XX年の論文で〇〇属に移された」)。

## idの決め方(決まり。過去に何度もトラブルの原因になった)

`id`は**実際の写真フォルダ名と完全に一致させる**。ズレると alias 表への追加作業が必要になる。

- 写真フォルダは `images/creatures/カテゴリー/生き物ID/` のほか、`images/creatures/other-insects/tombo/生き物ID/` のようにグループのフォルダの下にあることもある。生成スクリプトは2階層目も探すので、フォルダ名とidが同じなら対応表への追加は不要
- 写真フォルダ名が分からないときは、作業前にオーナーに確認する
- 「写真はあるけどmdがないのは？」と聞かれたら、写真フォルダ一覧と content の id を突き合わせて一覧にする。`failed/` フォルダは写真処理に失敗した写真の置き場で、生き物ではない

## dangerの書き方(決まり。カテゴリーごとに意味が違う)

生成スクリプトが文字列に含まれるキーワードで表示を自動判定する。

| カテゴリー | 書き方の例 | 判定 |
|---|---|---|
| ヘビ | `無毒` / `毒あり` / `猛毒` / `無毒・希少` | 毒の強さ(保護状況ではない) |
| 法的な保護あり | `捕獲・譲渡禁止(天然記念物)`、`捕獲禁止(鹿児島県希少野生動植物)` | 「禁止」を含むと赤い警告バッジ |
| レッドリストのみ | `環境省レッドリスト:絶滅危惧II類`、`環境省レッドリスト絶滅危惧II類(VU)` | 「レッドリスト」「絶滅危惧」で目立つタグ色 |
| 確認できない | 書かない | — |

**「希少=禁止」と決めつけない。** 条例(鹿児島県条例、奄美大島5市町村条例)や種の保存法の指定が確認できたときだけ「禁止」と書く。確認できなければレッドリストだけ書き、その旨をオーナーに伝える。
奄美島内では「生き物を持ち出さないで」という声明が出ており、採集を勧める書き方はしない。

## activity と night_observable(決まり。トップの写真に出るかが決まる)

トップの「ナイトツアーで出会える生き物」の写真は、`index.html` の次の条件で選ばれる:
個別ページがある、かつ `night_observable` が false でない、かつ「`activity: diurnal` なのに `night_observable: true` が無い」ものではない。

- 夜行性 → `activity: nocturnal`(トップに出る)
- 昼行性 → `activity: diurnal`(トップに出ない。図鑑・関連カードには出る)
- 昼行性だが夜に寝ている姿などを見られる → `activity: diurnal` + `night_observable: true`(例: オキナワキノボリトカゲ、ルリカケス)
- 夜行性でもツアーでは出会えない・出したくない → `night_observable: false`(例: チンメルマンセスジゲンゴロウ)

昼か夜かはオーナーが一番よく知っているので、分からなければ聞く。

- 水生昆虫は、夜の沢は危ないのでナイトツアーから外す → `night_observable: false`。夜行性かどうかを確かめていない種は `activity` を書かない。ただしトビイロゲンゴロウ・コガタノゲンゴロウ・オキナワスジゲンゴロウはツアーで見られる(`activity: nocturnal`)(2026-10-02 オーナーの指示)
- 夜行性でもツアーでは出会えない例: トラフズク、タイワンサイカブト(`activity: nocturnal` + `night_observable: false`)(2026-10-02)
- 夜行性でも、とても珍しくてツアーで見せられる自信がない種は外す → `night_observable: false`(例: アマミタカチホヘビ)(2026-10-02 オーナーの指示)
- 新しい種のmdを作るときは、`activity` と、ツアーで見られるかをオーナーに聞いてから書く。2026-10-02にオーナーと全112種を見直し、未記入の種は無くなった

## monthsの決め方(決まり。2026-09-30決定)

- `months:` は「ナイトツアーで観察しやすい時期」。オーナーが現場の感覚で決めるので、オーナーに聞いて書く(例: ヌマガエルは「5月から8月」→ `[5, 6, 7, 8]`)
- 資料の活動期・繁殖期は本文に書く。`months:` に自動で写さない(本文の時期は繁殖期などのことがあり、観察しやすい時期と同じとは限らない)。本文と `months:` は別の情報として両方残す
- 本文の「○月から○月」は、観察月の計算には使われない。観察月は日本語版mdの `months:` か、写真の撮影日の2つだけから決まる
- オーナーから聞けなかったら書かない。書かないと写真ファイル名の撮影日(`_YYYYMMDD_`)から自動集計され、`data/creatures.json` の `months_source` が `photos` になる(AIチャットは「撮影記録があります」と答える)
- 翻訳版(`.en.md` など)は日本語版の `months:` を使うので、翻訳mdで月を変えても反映されない

## サイトへの反映(決まり。コミットするとき)

リポジトリのルートで、ワークフロー `.github/workflows/process-creature-photos.yml` と同じ順に実行する:

```bash
python scripts/generate_creatures_json.py
rm -rf creatures
python scripts/generate_creature_pages.py
python scripts/generate_category_pages.py
python scripts/generate_zukan_page.py
python scripts/generate_highlights_page.py
rm -rf en/creatures es/creatures zh/creatures
python scripts/generate_creature_pages_i18n.py
python scripts/generate_creatures_json_i18n.py
python scripts/generate_category_pages_i18n.py
python scripts/generate_zukan_page_i18n.py
python scripts/check_translations.py
```

- 新しい種が増えると、ほかの生き物ページの関連カードも入れ替わるので、変更ファイルが数百になるのは正常(1ファイル1行程度の差分か確認する)
- `scripts/__pycache__/` の `*.cpython-311.pyc` はコミットしない(リポジトリに入っている `cpython-314` の方は消さない)
- `check_translations.py` は要確認0件になるのが正常(2026-09-30にHTMLコメントを数えないように直した)

## 報告に含めること(目安。形式は自由、中身は落とさない)

- `id` をどう決めたか(写真フォルダ名と一致しているか)
- `months` の根拠(オーナーから聞いたか、書かずに写真の自動集計に任せたか)
- `danger` を書いた根拠、または確認できず書かなかったこと
- 情報が薄い/不確かな箇所、ページを直接読めず検索の要約で確認した箇所
- 参考にした情報源のリンク
