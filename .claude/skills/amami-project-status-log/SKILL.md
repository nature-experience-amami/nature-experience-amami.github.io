# Amami PROJECT_STATUS.md 記録スキル

`PROJECT_STATUS.md`は、Claude・ChatGPT・Copilot・Geminiなど複数のAIが日をまたいで
引き継ぎながら作業するための状況記録ファイル。書式が崩れると引き継ぎが失敗するので、
厳密にルールを守ること。

## 記録ファイルの分け方(2026-09-30から)

- `AGENTS.md`: いつ・どの作業でも守る共通ルール
- `PROJECT_STATUS.md`: 今の状況(「現在の構成」「進行中の作業」「やることリスト」)と、「今月の変更履歴」
- `docs/history/YYYY-MM.md`: 過去の月の変更履歴(2026-09以前の記録は `docs/history/2026-09.md`。旧 `PROJECT_STATUS_updated.md` をそのまま移したもの)

## 絶対に守ること

1. **新しい記録は、`PROJECT_STATUS.md` の「今月の変更履歴」の末尾に追加する。**
   すでにある変更履歴の中身は削除・書き換えしない。
2. **月が変わったら、前の月の変更履歴を `docs/history/YYYY-MM.md`(YYYY-MMは記録した月)へそのまま移す。**
   1文字も書き換えない・要約しない・消さない。移したあとの「今月の変更履歴」は、新しい月の記録だけにする。
   `docs/history/` のファイルは、移したあとも書き換えない。
3. **「現在の構成」「進行中の作業」「やることリスト」は"生きた参照セクション"なので、最新の状態に上書きしてよい。**
   これらは履歴ではなく「今の正しい状態」を示す場所なので、古い記述が実態と合わなくなったら書き直す。
   終わった作業はやることリストから消してよい。ただし、書き直す際も「なぜ変わったか」が分かるよう、
   「今月の変更履歴」側にはその経緯を記録する。
4. 全員が守る決まりが新しくできたら、`PROJECT_STATUS.md` ではなく `AGENTS.md` に追加する。
5. ファイルをアップロードされて中身を確認する依頼を受けたときは、**必ず全文を読んでから**編集する。
   一部だけ見て「ここは古い」と判断しない。

## 1エントリの型(変更履歴に追加する内容)

```markdown
### YYYY-MM-DD 見出し(何をしたかが一目で分かる短い日本語)

- 変更内容を箇条書きで(何を・なぜ・どう直したか)
- 未完了事項: 次にやるべきことがあれば明記
- Commit SHA: あれば記載、無ければ「なし(未commit)」
- Push: 済み/未確認/未実施 のいずれかを明記

（担当: 作業したAIの通称。例: Claude／くろちゃん、Copilot、ChatGPT／こぱ、Gemini）
```

- 日付は実際の作業日(今日の日付)を使う
- 「担当」は必ず書く。複数AIが同じ日に別々の作業をした場合は、見出しを分けて別エントリにする
- Commit SHAやPush状況が本当に分からない場合は、憶測で書かず「未確認」と書く

## 複数のAIが別々にPROJECT_STATUS.mdを更新していた場合の統合手順

1. 両方のファイルを全文読む
2. 「今月の変更履歴」はそれぞれの記録をすべて残し、日付順にマージする(内容が重複していても両方残してよい。
   重複があること自体が「並行作業していた」という記録になる)
3. 「現在の構成」「進行中の作業」「やることリスト」などの生きたセクションは、**より新しい情報を反映して1本化**する
   (例: 片方の記録では「未着手」となっている作業が、もう片方では「完了」になっていれば、完了の方を採用する)
4. 矛盾する記述(片方は「pushした」、もう片方は「未push」など)を見つけたら、憶測で統一せず、
   ユーザーに確認する
5. 統合後のファイルは、元のファイル名`PROJECT_STATUS.md`のまま、ユーザーに渡して上書きしてもらう

## 記録すべきタイミング

明示的に頼まれたときはもちろん記録するが、次のような区切りでは**記録してよいか一言確認する**とよい。

- 新しい技術的な仕組み(スクリプト・テンプレート)を作った/作り直した
- サイト全体に関わる方針を決めた(SAFETY文言、カテゴリー分類、危険度の判定ロジックなど)
- 不具合の原因を特定して直した
- 一つの作業の区切り(①〜③のような番号付きタスクが完了した)

日々の細かいやり取り(ファイルの上書き先を教えた、コマンドの打ち間違いを直した、など)は記録しなくてよい。
